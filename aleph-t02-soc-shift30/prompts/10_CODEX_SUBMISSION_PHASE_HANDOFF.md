## 8. PDF의 목적과 독자

PDF는 기능 목록을 옮긴 설명서가 아니라, 요구사항을 해석하고 설계·구현·검증한
과정을 보여주는 작업 기록이자 포트폴리오다. 평가자가 처음 게임을 보는 사람이라는
점을 기준으로 쓴다.

문서 전체가 다음 질문에 답해야 한다.

- 처음 보는 사람이 30초 안에 목적과 조작을 이해할 수 있는가?
- 요구사항이 실제 화면과 검사 기록으로 검증되는가?
- 왜 이 규칙과 UX를 선택했는지 설명할 수 있는가?
- AI가 아니라 사용자가 최종 방향을 판단했다는 사실이 드러나는가?
- 몇 달 뒤 다시 봐도 문제 해결 과정과 성장 기록으로 쓸 수 있는가?

핵심 메시지는 “게임을 만들었다”가 아니라 다음과 같다.

> 요구사항을 기능과 검사로 바꾸고, 복잡한 SOC 판단을 초심자가 이해할 수 있는
> ALLOW/BLOCK 경험으로 단순화했으며, 실제 배포 환경까지 검증했다.

단, 마지막 문장은 실제 증거가 있는 범위까지만 주장한다.

## 9. PDF가 보여줘야 할 이야기 구조

기능을 나열하지 말고 각 주요 장을 다음 흐름으로 구성한다.

`문제·요구사항 → 사용자의 해석 → 설계 판단 → 실제 구현 화면 → 검증 방법 →
관찰 결과 → 배운 점`

특히 다음 판단이 사용자 자신의 결정으로 드러나야 한다.

- 기능 수보다 초심자 전달력과 완성도를 우선한 이유
- 복잡한 네트워크 시뮬레이션 대신 ALLOW/BLOCK 두 조작으로 줄인 이유
- 오탐과 미탐을 별개 실패로 다룬 이유
- 화면 전체를 픽셀 폰트로 만들지 않고 도트 감성을 아이콘과 시각 요소에 제한한 이유
- AI 제안을 그대로 채택하지 않고 범위 밖 기능과 불필요한 복잡성을 제거한 과정

사용자가 실제로 판단하거나 확인하지 않은 일을 사용자 서사로 만들지 않는다.

## 10. 권장 페이지 구성

분량보다 페이지의 역할을 우선한다. 같은 증거를 여러 페이지에서 반복하지 않는다.

1. **표지** — 과제명, 게임명, 한 줄 설명, 공개 URL, 작성일, 현재 준비 상태
2. **과제 해석** — 요구사항을 어떤 플레이 경험과 검사 항목으로 바꿨는가
3. **초심자를 위한 핵심 규칙** — 30초, ALLOW/BLOCK, 성공·실패·재시작
4. **설계 판단** — SOC 맥락, 오탐·미탐, 메모·전화·인수인계서의 역할
5. **한 판의 흐름** — 시작 → 플레이 → 판정 변화 → 성공/실패 → 재시작
6. **PC 안정성 검증** — 1366×768, 1920×1080, 입력, 포커스, 일시정지, 콘솔
7. **저장과 복구** — 초기화 값, 보존 값, 손상값 fallback
8. **손맛과 선택권** — 사건 효과, BGM/효과음, 음소거, 움직임 줄이기
9. **난이도 판단** — 실제 20회 기록의 범위·중앙값·반복 실패 원인과 최종값
   3000ms 선택 근거
10. **AI 협업과 사용자 판단** — 맡긴 일, 활용한 결과, 거절·수정·직접 결정한 일
11. **완료 체크리스트** — 모든 요구사항, 판정, 증거 위치, 남은 항목
12. **검증 안내서와 제출 정보** — 3단계 안내, AI 3줄, URL, 확인 파일
13. **회고** — 이번 과업을 통해 증명한 능력과 다음에 개선할 점

페이지 수를 억지로 맞추지 않는다. 근거가 없는 장은 만들지 않고, 두 장의 내용이
겹치면 합친다.

## 11. 이미지 선택과 캡션 규칙

`실행 이미지/`의 파일을 먼저 육안으로 열어 현재 배포본과 맞는지, 개인정보가
없는지 확인한 뒤 사용한다. 파일명만 보고 채택하지 않는다.

각 이미지에는 다음 세 가지가 있어야 한다.

1. **증명하려는 요구사항**
2. **평가자가 봐야 할 화면 위치 또는 값**
3. **실제 관찰 결과**

좋은 캡션 예시:

> 판정 전후 `SCORE 0→100`, `COMBO ×0→×1`로 한 번의 입력이 한 번의 상태
> 변화로 반영됨을 확인했다.

나쁜 캡션 예시:

> 게임 플레이 화면입니다.

가능하면 화살표, 테두리, 번호 같은 최소한의 강조를 사용하되 원본 수치와 UI를
가리지 않는다. 설명 없는 스크린샷, 같은 화면의 반복, 읽을 수 없을 정도로 작은
이미지는 넣지 않는다.

`E03`·`E04`처럼 현재 배포 직전 화면인 이미지는 최신 화면인 것처럼 쓰지 않는다.
사용하려면 촬영 시점과 차이를 캡션에 밝히거나 현재 빌드로 다시 찍는다.

## 12. 검증 안내서와 AI 3줄

검증 안내서는 다음 네 제목을 그대로 사용한다.

- 어디로 가나요
- 무엇을 하나요 — 공개 주소에서 바로 실행 가능한 최대 3단계
- 무엇이 보이면 통과인가요
- 안 될 때

오너가 URL을 연 뒤 15초 안에 현재 결과를 판단할 수 있게 짧게 쓴다.

AI 사용 기록은 제출 화면과 PDF에 **완전히 같은 문장**을 넣으며, 정확히 세 줄,
각 줄 한 문장으로 쓴다.

1. AI에게 요청한 일
2. 실제로 활용한 AI 결과
3. 사용자가 직접 판단·확인·수정하거나 거절한 일

“AI가 모두 만들었다”거나 “AI는 보조했을 뿐이다” 같은 추상 문장 대신 실제
프로젝트의 구체적인 판단을 쓴다. 사용자가 직접 하지 않은 테스트를 했다고 쓰지 않는다.

## 13. 디자인 원칙

우선순위는 `가독성 > 정보 전달 > 일관성 > 장식`이다.

- 본문과 캡션을 축소해 억지로 한 페이지에 넣지 않는다.
- 제목 단계, 본문 크기, 여백, 이미지 폭, 캡션 형식을 끝까지 통일한다.
- 페이지마다 하나의 중심 질문 또는 증명 목적을 둔다.
- 게임의 나이트 시프트 콘솔 분위기는 표지·구분선·강조색에 절제해서 반영한다.
- 긴 문단보다 짧은 설명, 비교표, 화면과 근거의 가까운 배치를 우선한다.
- 화려한 장식, 의미 없는 미사여구, AI가 쓴 듯한 과장된 문구를 피한다.
- 개인정보, 사용자 경로, 계정 화면, 토큰, 다른 탭이나 북마크가 보이면 이미지를
  사용하지 말고 안전하게 다시 만든다.

## 14. PDF 제작 절차

1. `notes/11-final-audit.md`와 실제 캡처를 대조해 사용할 수 있는 주장만 목록화한다.
2. 각 페이지에 “이 페이지가 증명할 한 가지”를 먼저 적고 필요한 증거를 배치한다.
3. 초안을 만든 뒤 문장과 캡션의 사실성을 원본 기록과 교차 확인한다.
4. PDF로 내보낸다.
5. **모든 페이지를 이미지로 렌더링해 육안 검사한다.**
6. 잘림, 글자 깨짐, 작은 글씨, 빈 페이지, 오래된 이미지, 어긋난 캡션, 개인정보를
   수정하고 다시 내보낸다.
7. 제출 URL, AI 3줄, 체크박스 주장, 선택할 PDF의 내용이 서로 같은지 확인한다.

PDF 파일을 실제로 생성하거나 수정할 때는 작업 환경의 PDF 제작·검증 지침을
사용하고, 렌더링 확인 없이 완성이라고 보고하지 않는다.

## 15. 페이지별 품질 점검

각 페이지를 완료할 때 다음 질문에 모두 답한다.

1. 이 페이지가 왜 필요한가?
2. 처음 보는 평가자가 한 번에 이해할 수 있는가?
3. 모든 주장에 실제 근거가 있는가?
4. 이미지가 주장한 내용을 정말 증명하는가?
5. 불필요하거나 반복되는 내용은 없는가?
6. 앞뒤 페이지와 자연스럽게 연결되는가?
7. 사용자의 직접 판단이 사실에 맞게 드러나는가?

최종 PDF 전체에서도 다음을 확인한다.

- 모든 필수 요구사항의 판정과 증거가 있다.
- `미통과`와 `증거 부족`이 미화되거나 숨겨지지 않았다.
- 공개 URL은 직접 검사한 현재 주소다.
- AI 3줄이 제출 입력과 글자 단위로 같다.
- 모든 페이지에 잘림·깨진 글꼴·개인정보·비밀값이 없다.
- 선택할 파일 하나가 현재 결과를 대표하며 실제로 열린다.

## 16. 실제 제출 화면 계약

2026-08-21에 사용자가 제공한 제출 화면을 현재 UI의 source of truth로 사용한다.
화면에는 다음 항목이 있다.

### 제출 조건 체크박스 4개

표시 문구를 임의로 바꾸지 않는다.

1. `결과물 URL 또는 실행 결과`
2. `실행 캡처`
3. `AI 사용 기록`
4. `스스로 점검표`

체크박스는 단순 확인 버튼이 아니라 제출할 내용에 대한 사실 주장이다. 현재 PDF와
증거가 해당 주장을 실제로 뒷받침할 때만 `체크 가능`으로 보고한다. 최신 감사상
35개 요구사항이 모두 통과했으므로 최종 PDF 교차 확인 뒤 네 항목 모두 체크 가능하다.

### 결과물 URL (선택)

화면상 선택 항목이지만 공개 웹 게임이므로 아래 주소를 입력한다.

```text
https://myeongjundev.github.io/mini-game/
```

입력 직전에 이 주소를 직접 열어 현재 공개본이 정상인지 다시 확인한다. PDF 표지와
검증 안내서에 적힌 URL도 글자 단위로 같아야 한다.

### AI 사용 기록 3줄

현재 화면의 정확한 의미는 다음과 같다.

```text
1줄: 무엇을 요청했는지
2줄: 어떤 답을 활용했는지
3줄: 내가 직접 확인·수정한 내용
```

입력창 아래 안내대로 **빈 줄 없이 정확히 3줄**을 작성한다. 각 줄은 한 문장으로
완결하고, PDF에 들어가는 세 문장과 제출 입력을 완전히 동일하게 유지한다.

### 확인할 파일 선택

- 과제 결과를 확인할 **최종 비공개 PDF 한 개**를 선택한다.
- 화면 안내상 선택한 파일은 비공개로 업로드되고 학생 본인, 담당 강사와 운영자만
  확인할 수 있다.
- 그렇더라도 개인정보, 비밀번호, 토큰, API 키, 사용자 경로는 PDF에 넣지 않는다.
- 선택 직전에 파일을 실제로 열고 모든 페이지가 현재 결과를 나타내는지 확인한다.
- 초안, 오래된 PDF, 렌더링 전 원본을 잘못 고르지 않도록 절대 경로와 파일명을
  완료 보고에 적는다.

### 제출 버튼과 제출 시각

- `과제 제출`은 제출 시각을 기록하는 외부 상태 변경이다.
- 화면 안내상 마감 전에는 언제든 다시 제출할 수 있지만, 이를 제출 허가로
  해석하지 않는다.
- 사용자가 명시적으로 제출을 승인하기 전에는 버튼을 누르지 않는다.
- 승인 후 제출했다면 완료 화면과 실제 제출 시각을 기록한다.

### 제출 직전 60초 확인

1. 네 체크박스 각각에 대응하는 최신 증거가 있는지 확인한다.
2. 공개 URL을 새로 열어 정상 실행을 확인한다.
3. AI 입력이 빈 줄 없는 정확히 3줄인지 확인한다.
4. 선택한 PDF를 다시 열어 잘림, 깨진 글꼴, 개인정보와 오래된 증거가 없는지 본다.
5. URL, AI 3줄, PDF 내용, 체크박스 주장이 서로 일치하는지 대조한다.
6. 현재 준비 판정과 사용자 제출 허가를 마지막으로 확인한다.

## 17. 제작 완료 보고 형식

PDF를 완성한 뒤 아래 순서로 보고한다.

```text
상태: [제출 가능 / 조건부 제출 가능 / 제출 불가]

남은 사용자 행동
1. [가장 긴급한 실제 행동]

결과물 URL
https://myeongjundev.github.io/mini-game/

AI 사용 기록 3줄
1줄: [한 문장]
2줄: [한 문장]
3줄: [한 문장]

확인할 파일
[최종 PDF 절대 경로와 파일명]

체크박스
- 결과물 URL 또는 실행 결과: [체크 가능 / 불가]
- 실행 캡처: [체크 가능 / 불가]
- AI 사용 기록: [체크 가능 / 불가]
- 스스로 점검표: [체크 가능 / 불가]

검증
- [PDF 페이지 수와 렌더링 검사 결과]
- [잘림·글자 깨짐·개인정보·비밀값 결과]
- [URL·AI 3줄·체크박스 교차 확인 결과]

남은 미통과·증거 부족
- [요구사항 / 판정 / 필요한 행동]
```

사용자의 명시적 허가가 있기 전에는 최종 제출 버튼을 누르지 않는다.
