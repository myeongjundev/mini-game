# AI Decision Log

이 문서는 과제의 `AI 3줄`과 개발자 판단 근거를 남긴다.

## Decision 001 — 퀴즈 대신 SOC 판단 게임
### AI 제안
네트워크 퀴즈, 패킷 러너, 방화벽 피하기 등 여러 후보.

### 내가 판단
같은 반에서 30초/목숨3/네트워크 퀴즈 사례가 있어,
단순 문제풀이와 차별화하기 위해 SOC 이벤트 판단 구조 선택.

### 버린 것
복잡한 네트워크 시뮬레이션.

### AI 제안
AI Threat Recommendation 기능.

## Decision 003 — Backend 역할 최소화
### AI 제안
서버 판정, 사용자 계정, 랭킹 등.

### 내가 판단
게임 반응성은 프론트에서 처리하고,
Spring은 플레이 기록/통계부터 담당.

### 버린 것

## Decision 004 — 백엔드를 T02 범위에서 완전히 제외
Decision 003의 갱신.

### AI 제안
React + Spring Boot 모노레포로 프론트와 백엔드를 함께 구성.

### 내가 판단
T02의 완료 기준은 "공개 주소에서 실행"인데 Spring은 GitHub Pages에 올릴 수 없다.
별도 서버를 붙이면 그 서버가 죽었을 때 검증 안내서 전체가 흔들린다.
T02는 정적 프론트로 완결하고, 백엔드는 이후 Incident Journal 과제로 분리한다.

### 버린 것
T02 단계의 Spring 백엔드, 서버 점수 판정, API 계약 문서.

## Decision 005 — 도트를 글자에서 빼고 아이콘에만 남김
### AI 제안
흔한 Dark Navy + Cyan 관제 대시보드 톤, 또는 8비트 도트 전면 적용 중 택일.
정보 판독 속도를 근거로 픽셀 폰트를 쓰지 말 것을 권고받음.

### 내가 판단
이 게임은 액션이 아니라 1.4초 안에 사실 4개를 읽는 **읽기 게임**이다.
픽셀 폰트로 `FAILED LOGIN: 87`을 읽다 실패하면 게임이 아니라 폰트가 실패한 것이 된다.
그래서 정보 텍스트는 모노스페이스로 두되, 도트를 완전히 버리지는 않고
카테고리 아이콘·라이프·판정 마크·토글·등급 도장에 남겨 표현 정체성을 지켰다.
배경도 흔한 네이비 대신 뉴트럴 다크로 내렸다.

### 버린 것
픽셀 폰트 전면 적용, CRT 스캔라인 오버레이, 네이비+시안 기본 조합.

## Decision 006 — 색을 오탐·미탐 2축으로 배치
### AI 제안
정상은 초록, 위험은 빨강이라는 일반적인 관제 UI 1축 배색.

### 내가 판단
이 게임의 실패는 한 종류가 아니다.
정상을 막으면 서비스가 죽고(오탐), 위협을 통과시키면 침해가 일어난다(미탐).
그래서 BLOCK 버튼을 빨강이 아니라 앰버로 두어 "차단은 공짜가 아니다"를 버튼 단계에서 드러내고,
빨강은 위협과 미탐에만 썼다. 결과 화면에서 두 실수가 다른 색 막대로 갈린다.
색만으로 구분되지 않도록 아이콘과 텍스트를 함께 붙였다.

### 버린 것
BLOCK = 빨강이라는 관습적 배색, 초록 상시 표시.

---

## Decision 007 — 스택은 AI 권고를 따르지 않음
### AI 제안
배포가 단순하고 깨질 여지가 적다는 이유로 순수 HTML·CSS·JavaScript를 권고받음.
문서 폴더는 문서 전용으로 두고 소스는 별도 폴더에 두는 안도 함께 제안받음.

### 내가 판단
T02만 보면 순수 정적 파일이 맞지만, 이 프로젝트는 이후 ALEPH 과제
(Incident Journal, 기록 검색, AI 분석가)로 확장할 출발점이다.
지금 React + TypeScript로 시작하면 그때 다시 옮기는 비용이 사라진다.
문서 폴더도 문서 전용으로 두지 않고 프로젝트 루트로 승격시켜 문서와 코드를 한곳에 뒀다.

### 버린 것
순수 정적 파일 구성, 문서와 코드의 분리 배치.

---

## Decision 008 — 난이도 상수는 등장 간격
### AI 제안
속도, 등장 간격, 제한 시간, 판정 범위 네 가지 후보.

### 내가 판단
제한 시간 30초는 게임의 정체성이자 제목이라 건드릴 수 없다.
속도와 판정 범위는 이 게임에 존재하지 않는다. 이동 오브젝트도 타이밍 판정도 없기 때문이다.
등장 간격만이 "읽고 판단할 시간"을 직접 줄여 난이도와의 인과가 명확하고,
오탐·미탐 수치에 미치는 영향을 그대로 관찰할 수 있다.

### 버린 것
제한 시간 변경, 복수 상수 동시 변경.

## 최종 AI 3줄 작성란

> 아래는 위 결정 기록을 근거로 한 초안이다. 구현이 끝난 뒤 실제 작업과 대조해 확정한다.
> 같은 내용이 `mini-game/notes/06-submission-plan.md`에도 있으며, 제출 원본은 그쪽을 쓴다.

### AI에게 맡긴 일
게임 아이디어 후보 비교, 경보 데이터셋과 문서 구조 초안, 픽셀 아이콘 그리드 초안,
검사표 설계, 구현 과정의 반복 작업을 AI에게 맡겼다.

### 내가 판단한 일
후보 5개 중 SOC SHIFT:30을 직접 골랐고, 30초 안에 이해되도록 관제 업무를
ALLOW / BLOCK 두 조작으로 줄였다. 오탐과 미탐을 별개의 실패로 설계하고
각각 앰버와 레드로 색을 나눠, 차단이 공짜가 아니라는 점이 화면에 드러나게 했다.
난이도 상수도 이 게임에 실제로 존재하는 변수인 등장 간격으로 직접 정했다.

### AI 말을 안 들은 일
AI는 배포가 단순하다는 이유로 순수 HTML·CSS·JS를 권했지만,
이후 ALEPH 과제로 확장할 것을 고려해 Vite + React + TypeScript를 직접 선택했다.
문서 폴더를 문서 전용으로 두라는 제안도 받아들이지 않고 프로젝트 루트로 승격시켰다.
도트 표현은 글자에서 빼라는 조언만 받아들이고, 아이콘에는 그대로 남겼다.
초기 아이디어였던 실시간 네트워크 시뮬레이션과 LLM 연동 기능은 과제 범위를 넘어서므로 넣지 않았다.
