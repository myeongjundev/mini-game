## 주요 결정과 이유

과제의 "AI 말을 안 들은 일"과 직결되는 판단들입니다.
정리본은 `aleph-t02-soc-shift30/docs/AI_DECISION_LOG.md`에 있습니다.

### 스택 — Vite + React + TypeScript
AI는 배포가 단순하다는 이유로 순수 정적 파일을 권했지만, 이후 ALEPH 과제
확장을 고려해 React를 직접 선택했습니다. 문서 폴더도 프로젝트 루트로 승격시켰습니다.

### 백엔드를 T02 범위 밖으로
Spring은 GitHub Pages에 올릴 수 없고, 별도 서버가 죽으면 "공개 주소에서 실행"
기준 전체가 흔들립니다. 이후 Incident Journal 과제로 분리했습니다.

### 도트는 글자에서 빼고 아이콘에만
1.4초에 사실 4줄을 읽는 게임이라 픽셀 폰트를 쓰면 판단 실패가 폰트 탓이 됩니다.
카테고리·라이프·판정·토글·등급에만 도트를 남겨 정체성은 지켰습니다.

### 색을 오탐·미탐 2축으로
BLOCK 버튼을 빨강이 아니라 앰버로 뒀습니다. 차단이 공짜가 아니라는 감각을
버튼 단계에서 주고, 그 앰버가 결과 화면의 오탐 막대로 이어집니다.

### 미판정을 별도 실패로 (C안)
제한시간 내 무입력 시 라이프 -1, 콤보 0, 점수 0. `reviewed`는 올리지 않아
Accuracy가 "검토한 것 중 맞힌 비율"로 유지됩니다.
아무것도 안 하면 반드시 지므로 30초의 긴장이 유지됩니다.

### 난이도 상수는 등장 간격
제한 시간 30초는 정체성이라 못 건드리고, 속도·판정 범위는 이 게임에 없습니다.
등장 간격만 "읽고 판단할 시간"을 직접 줄여 인과가 명확합니다.

### 저장소를 public으로

## 리뷰 지적 사항 (인트로·로비)

- **C-1** 판단 가이드 회귀 — 로비 개편에서 조작키 안내와 예시 카드 2장이 사라짐.

## 가이드를 4쪽으로 나눈 이유

동기들 피드백이 "설명이 부족하다"가 아니라 **"내용을 이해 못 하겠다"**였습니다.
분량 문제가 아니라 가르치는 방식의 문제였습니다.

경보 15개를 다시 보니 정답을 가르는 것은 거의 항상 **행위가 아니라 자격**이었습니다.

| 쌍 | 같은 것 | 다른 것 | 정답 |
|---|---|---|---|
| `exfil` / `backup-job` | 새벽 시간, 몇 GB 전송, 표시 붙음 | 목적지가 Unknown Host / Registered Backup Server | BLOCK / ALLOW |
| `ssh-brute` / `typo-login` | 로그인 실패 다수 | 출처가 Unknown / 등록 기기이고 결국 성공 | BLOCK / ALLOW |
| `contractor-proddb` | MFA 통과 | 계약직의 운영 DB 첫 접근 | BLOCK |

특히 `exfil`과 `backup-job`은 **거의 같은 카드인데 목적지 한 줄에서 갈립니다.**
이 한 쌍을 3쪽에 그대로 보여주는 것이 설명 열 줄보다 낫다고 판단했습니다.
두 카드는 `ALERTS`에서 직접 읽으므로 데이터가 바뀌면 가이드도 함께 바뀝니다.

4쪽에는 `f8d3772`에서 사라졌던 오탐·미탐 구분을 되살렸습니다. 앰버와 빨강
2축 설계가 결과 화면의 막대와 이어집니다.

### 이유는 이미 데이터에 있었습니다

두 번째 피드백은 "결정적 항목은 알겠는데 그래서 왜 허용이냐"였습니다.
새 문구를 쓸 필요가 없었습니다. 경보마다 `explanation`이 이미 있었고,
판이 끝난 뒤 SHIFT LOG에서만 보이고 있었습니다.

```
등록된 기기가 알려진 서비스로 보내는 정상 암호화 트래픽이다
40초에 87회 실패는 사람이 아니라 자동화된 무차별 대입이다
```

가이드가 이 값을 직접 읽으므로 경보 데이터를 고치면 가이드도 함께 바뀝니다.
설명을 따로 쓰면 둘이 어긋나기 시작합니다.

카드 두 장을 나란히 두면 폭이 165px라 설명이 네 줄로 깨집니다. 쪽을 나눠
한 장씩 넓게 보여주고, 제목을 **"통과시키는 경보" "막는 경보"**로 두어
질문에 그대로 답하게 했습니다.

### 구현에서 두 번 틀린 것

**하나.** 처음에는 제목·본문·쪽 넘김을 한 덩어리로 스크롤시켰습니다.
그랬더니 내용이 긴 쪽에서 **넘김 버튼이 유리 밖으로 밀려 다음 쪽으로 갈 수
없었습니다.** 제목과 넘김을 고정하고 본문만 스크롤하도록 고쳤습니다.

**둘.** 설명을 넣자 본문이 148px인데 219px가 필요해졌습니다. 정작 추가한
설명이 접혀서 안 보이는 상태였습니다. 세 가지로 줄였습니다.

- 가이드에서는 콘솔 머리글(`SOC NODE // 01`)을 접습니다. 장식인데 이 한 줄이
  설명을 밀어냅니다
- 각 쪽 도입문을 한 줄로 줄였습니다
- 판정 줄과 설명 사이 여백을 좁히고 설명의 구분선을 없앴습니다

넘침이 71px에서 8px이 되어 설명이 스크롤 없이 보입니다. 둘 다 **"넣었으니
됐다"로 끝냈으면 사용자에게는 없는 기능**이었습니다.

## MEMO — 근무 중 방해를 넣은 과정

"방해가 들어가면 재밌을 것 같다"에서 출발했습니다. 후보는 알림창, 비밀번호
입력, 상사의 전화 셋이었고 **알림창 하나만** 넣었습니다. 규칙 전문은
`docs/GAME_SPEC.md` 13절입니다.

### 방해를 순수한 비용으로 두지 않은 이유

방해가 시간만 뺏으면 짜증만 남습니다. 그래서 메모에 **뒤에 올 경보의 판단
근거**를 실었습니다. 읽으면 다음 판정이 쉬워집니다. 비용을 낼지 말지를
플레이어가 고릅니다.

메모 6장 중 정답이 ALLOW인 경보를 돕는 것 3장, BLOCK을 돕는 것 3장입니다.
**이 균형을 깨면 안 됩니다.** 전부 ALLOW를 도우면 "메모를 봤으면 통과"라는
새 정답표가 생깁니다. 카드에서 심각도를 뺀 것과 같은 이유입니다.

### 큐를 손대지 않고 짝을 맞춘 방법

경보 큐는 티어별 봉지입니다. 한 봉지를 다 뽑기 전에는 반복되지 않으므로
**그 티어의 경보는 해당 구간에 반드시 나옵니다.** 그래서 메모를 연결된
경보의 티어가 시작되기 전에 띄우기만 하면 짝이 자동으로 맞습니다.
큐에는 손대지 않았습니다.

슬롯을 경과 시간(3 / 7 / 12 / 16초)으로 고정한 것도 의도입니다.
`eventIntervalMs`를 바꿔도 메모 배치가 그대로라 **난이도 실험에 변수가
섞이지 않습니다.**

### 구현에서 세 번 틀린 것

세 번 다 사용자가 화면을 찍어 보내서 알았습니다.

**하나. 아이콘이 화면을 다 먹었습니다.**
`PixelIcon`은 `viewBox`만 내보내고 `width`/`height` 속성이 없었는데
`.memo-icon`에 크기 규칙을 빠뜨렸습니다. SVG가 부모를 다 채워 글자를
밀어냈습니다. CSS를 넣고, `PixelIcon`에도 속성을 안전망으로 추가했습니다.

이 건에서 **제가 한 사전 검증이 무효였습니다.** 손으로 쓴 목 컴포넌트에
실제 코드에는 없는 `width="24"`를 넣어두고 통과했다고 봤습니다.
목이 실물보다 관대하면 검증이 아니라 자기 확인입니다.

**둘. 판정이 영구히 막혔습니다.**
`state.activeMemo !== null`이 문제였습니다. 개발 서버에서 HMR로 코드만
갱신되면 리듀서 상태는 이전 판 그대로라 `activeMemo` 필드 자체가 없고,
`undefined !== null`이 참이라 **판정을 계속 거부**했습니다.

화면 쪽은 `activeMemo ? 메모 : 버튼`이라 `undefined`면 버튼을 정상으로
그립니다. 그래서 **보이기엔 멀쩡한데 눌러도 반응이 없는** 형태였습니다.
세 곳 모두 참/거짓 판정으로 바꾸고, `activeMemo`를 **지운** 상태로 도는
회귀 테스트를 붙였습니다.

**셋. 메모가 뜬 경보는 피할 수 없는 미판정이었습니다.**
경보 한 장의 수명은 `eventIntervalMs`, 즉 **1.4초**입니다. 그 안에서
메모를 알아채고 읽고 닫고 경보 4줄을 다시 읽고 판정해야 했습니다.
메모 본문 한 줄 읽는 데만 2초가 넘습니다. **실력과 무관한 손실**입니다.

`GAME_SPEC` 13.10에 비밀번호 연타를 뺀 이유로 "5회 연타는 경보 한 장
창(1.4초)의 70%를 먹어 피할 수 없는 라이프 손실이 된다"고 적어두고,
**같은 계산을 메모에는 적용하지 않았습니다.** 공정성 규칙을 등장 시점에만
걸고 시계는 계속 돌린 것이 원인입니다.

세 가지를 함께 고쳤습니다.

- 메모가 떠 있는 동안 **현재 경보의 제한시간을 멈춥니다.** 30초 근무
  시계는 계속 흐르므로 비용은 그대로 남습니다
- 메모를 **경보 카드 위로** 옮겼습니다. 화면 아래는 판정 표시의 자리라
  둘이 겹쳐서 서로를 가리고 있었습니다. 시선도 이미 카드에 있습니다
- 판정 버튼을 지우지 않고 **비활성으로** 남깁니다. 버튼이 사라지면
  "버튼이 어디 갔지"가 되지만, 회색 버튼은 "지금은 막혔구나"가 됩니다

1366×768 실측입니다. 메모 229–559(경보 카드와 일치), 판정 버튼 575–630
(안 움직임), 판정 표시 640–729. **겹침이 사라졌고** 세로·가로 넘침도 0입니다.

## 로비 반응형 (2026-08-19)

큰 모니터에서 로비가 작고 모바일에서 CRT가 좁다는 요청이었습니다.

**데스크톱.** 셸 상한을 1180px → 1440px로 올리되 고정이 아니라 뷰포트

```css
width: min(100%, 1440px, calc((100vh - var(--gap-lg) * 2 - 2px) * 1672 / 941 + 2px));
```

`- 2px … + 2px`가 핵심입니다. `.app-shell`에 1px 테두리가 있고
`box-sizing: border-box`라 이걸 빼지 않으면 셸이 씬보다 2px 높아집니다.
**1366×768에서 세로 스크롤 1px이 실제로 났고** 그걸 보고 고쳤습니다.

**모바일.** 전체를 줄이는 대신 크롭을 유리 중심으로 옮겼습니다. 기본

치우쳐 있었고, 그 상태로는 폭을 85.12%(= 42.56 × 2) 넘게 키우면 왼쪽이
잘립니다. **목표인 88~92%가 구조적으로 불가능했습니다.**
`object-position: 43.91%`로 옮겨 유리를 씬 중앙에 놓고 1.25 → 1.44배로
올렸습니다. 계산 근거는 `DESIGN_TOKENS.md` 9절에 있습니다.

## 모바일 판정 기록이 글자 단위로 쪼개지던 문제 (2026-08-19)

`.shift-log-head`가 `24px minmax(0,1fr) auto auto auto` 다섯 칸이라
좁은 화면에서 심각도·판단·결과가 폭을 먼저 가져갔습니다. 390px에서 제목
칸이 **9px**만 남았고 `overflow-wrap: anywhere`가 "SEQUENTIAL PORT PROBE"를
글자 단위로 쪼개 세로로 **285px**까지 늘렸습니다.

**경계값으로 풀려다 그게 틀린 접근이라는 걸 재보고 알았습니다.** 같은
390px에서도 `LOW ALLOW CORRECT`는 한 줄에 들어가지만
`CRITICAL BLOCK MISSED THREAT`는 261px이라 쓸 수 있는 257px을 넘습니다.
**몇 줄이 필요한지가 화면 폭이 아니라 내용 길이에 달려 있어서** 어떤
경계값을 잡아도 한쪽은 틀립니다.

그래서 칸을 고정하지 않고 줄바꿈에 맡겼습니다. 제목에 `flex-basis: 100%`를
줘 첫 줄을 통째로 쓰게 하고, 아이콘은 음수 마진으로 들여쓰기 밖에 내보내
첫 줄 폭을 먹지 않게 했습니다. 접힌 줄은 모두 제목과 같은 세로선에서
시작합니다. 641px 이상은 기존 그리드 그대로입니다.

## 메모 로그 (2026-08-20)

**자리.** 1320px 이상은 셸 오른쪽 바깥에 절대 위치로 띄웁니다. 셸이
가운데 그대로 있어 판이 시작될 때 화면이 옆으로 튀지 않습니다. 경계는
한쪽 여백이 `(V - 48 - 720) / 2`라 패널 240px + 간격 24px이 들어가려면
`V >= 1296`이어야 한다는 데서 나왔습니다.

그 아래는 판정 버튼 밑으로 흐르되 목록 높이를 104px로 묶었습니다.
**본편 화면이 로그 없이도 이미 세로가 넘치기 때문입니다** — 390×844에서
44px, 1280×720에서 19px. 기존 상태고 이번 변경 탓이 아닙니다. 넉 장을 다
펼치면 274px이 붙는데 묶으면 165px이고, 판정 버튼은 스크롤 없이 보입니다.

**결과 화면은 두 군데에 냅니다.** 목록만 두면 어느 공지가 어느 경보용이었는지
사람이 맞춰봐야 합니다. `Memo.alertId`와 `DecisionRecord.alertId`가 이미
이어져 있어서 판정 기록 항목 안에 그 경보의 공지를 붙였습니다. **틀린 경보
밑에 붙으면 "그 정보를 갖고 있었다"가 드러납니다.** 항목에만 붙이면 경보가
안 나온 공지가 사라지므로 오른쪽 목록도 함께 둡니다.

**여기서 설계 문제를 하나 발견했습니다.** 플레이 결과가 `SURVIVAL TIME 19.4s`
인데 `MEMOS READ 4 / 4`였습니다. 슬롯 3·4는 티어 3 경보를 돕는데 티어 3은
20초부터입니다. **20초를 못 넘기면 그 두 장은 가리킬 경보가 없었던 셈입니다.**
넉 장을 다 읽느라 근무 시간을 썼는데 절반이 헛돈 겁니다.

규칙은 바꾸지 않고 결과 화면에 "이 공지의 경보는 나오기 전에 근무가
끝났습니다"라고 표시만 했습니다. **실험 중에는 규칙을 고정해야 하므로,
20판에서 얼마나 자주 그러는지 보고 정하기로 했습니다.**

## 경보 제한시간을 1400에서 2000으로 올림 (2026-08-20)

플레이해보고 "공부가 되게 시간을 더 주자"는 판단이 나왔습니다. 재보니
숫자도 같은 방향이었습니다.

**1.4초는 읽는 데만 다 쓰였습니다.** 경보 한 장에 사실 항목이 4개인데,
라벨과 값과 신호를 네 번 훑고 판단까지 1.4초면 따져보는 게 아니라 반사로

**그리고 경보가 반복되고 있었습니다.** 티어 구간은 10초이고 티어당 경보는
5장인데, 1400ms면 구간당 7.1장이 뽑혀 봉지가 7초에 비고 같은 경보가 두 번
나옵니다. 실제 결과 화면에 `SEQUENTIAL PORT PROBE`가 두 번 찍혔습니다.

**2000이라는 값은 감이 아니라 데이터 크기에서 나왔습니다.** 10초 ÷ 2초 =

## 제한시간을 2000에서 3000으로 다시 올림 (2026-08-20)

**같은 값을 하루에 두 번 올렸습니다.** 위의 1400 → 2000 절은 그대로 둡니다.
지나간 판단을 덮어쓰면 왜 두 번 움직였는지가 사라집니다.

**이번엔 제가 잰 것이 아니라 동기들에게서 왔습니다.** "문제가 보여지는 시간이

2000을 하고도 촉박하다는 뜻이라 올리는 게 맞았습니다.

이걸 먼저 물은 이유는, **아니었으면 과교정이 됐을 것**이기 때문입니다.
이미 고친 문제에 두 번 대응하면 값이 근거 없이 커집니다.

## 메모 중 키를 누르면 판이 그 자리에서 멈추던 문제 (2026-08-20)

플레이 중 **시계는 흐르는데 경보가 안 넘어가고 키도 안 먹는** 상태가 났습니다.
`dfd6d2f`와 증상이 같아 보였지만 원인은 다른 곳이었습니다.

**원인.** `handleDecide`가 리듀서에 보내기 **전에** `resolvedRef`에 "이 경보는
처리됨"을 먼저 찍습니다. 그런데 `decideCurrentAlert`는 메모가 떠 있으면 그
판정을 거부합니다. 그래서 메모 중 A·D·←·→ 를 한 번이라도 누르면 화면은
처리됐다고 기록했는데 상태 기계는 아무것도 하지 않은 상태가 됩니다.

그 뒤로는 이렇게 됩니다.

- 판정 입력이 전부 `resolvedRef.current === currentAlertId`에 막힌다
- `handleTimeout`도 **같은 가드**에 막혀 경보가 만료되지 않는다
- `currentAlert`가 null이 안 되니 `PRESENT_ALERT`도 돌지 않는다
- `TICK`은 무관하게 흐른다 → 근무 시계만 계속 준다

판정 버튼은 메모 중 비활성이라 마우스로는 이 경로에 닿지 않습니다.
**키보드에만 메모 조건이 없었습니다.** 메모는 판정하려는 순간에 끼어들므로
그때 키를 누를 확률이 높습니다.

**재현.** jsdom에서 rAF를 직접 돌려 4초까지 진행시키면 메모가 뜹니다.
그 상태에서 `a`를 누르고 메모를 닫으면 경보가 영원히 남습니다.

```
[메모 등장]  t=4050  MEMO  card="DNS QUERY"  TIME 26.0s
[닫은 뒤 a] t=4050  ----  card="DNS QUERY"  TIME 26.0s
[+10500ms]  t=14550 ----  card="DNS QUERY"  TIME 15.5s
```

**고친 것 둘.**

- `handleDecide`에 `isMemoOpen`을 넣었습니다. 리듀서가 거부할 판정은 보내지
  않습니다. 비활성 버튼과 키보드가 같은 규칙을 따르게 됩니다
- `resolvedRef`를 되돌리는 조건을 `[currentAlertId]`에서 **매 렌더**로
  바꿨습니다. 렌더가 한 번 돌았으면 리듀서는 그 판정을 이미 처리했고,
  받아들여졌다면 경보가 바뀌어 있습니다. 이 표시의 역할은 같은 프레임 안의
  연타를 막는 것 하나뿐인데 그보다 오래 살아 있었습니다

**두 번째가 더 중요합니다.** 첫 번째만 고치면 이번 증상만 없어집니다.
리듀서가 판정을 거부하는 경로가 새로 생기면 같은 멈춤이 다시 납니다.
`dfd6d2f`(`undefined !== null`)도 **화면이 가진 판정 상태와 상태 기계가 가진
판정 상태가 어긋난** 같은 계열이었습니다. 낙관적으로 먼저 찍고 나중에 안
맞으면 되돌리지 않는 구조 자체가 원인입니다.

**검사 4개를 붙였습니다** (`src/App.memo-hang.test.tsx`). 고치기 전으로
되돌려 3개가 실패하는 것을 확인했습니다. 나머지 1개(메모 중 입력은 무시된다)는
원래 동작이라 양쪽에서 통과합니다.

마지막 검사는 처음에 "근무가 끝까지 간다"였는데 **고치기 전에도 통과했습니다.**
근무 시계는 멈춘 것과 무관하게 30초에 끝나기 때문입니다. 멈춘 경보는 판정도
만료도 되지 않아 판정 기록에 아예 오르지 않는다는 쪽으로 바꿨습니다.
**통과하는 검사를 쓰는 것과 구분하는 검사를 쓰는 것은 다릅니다.**

렌더 단계에서 `inert`를 걸면 커밋 때 먼저 사라질 줄 알았는데 아니었습니다.
결국 **포커스 복원을 여는 쪽으로 옮겼습니다.** 부모의 effect는 inert를 지운
커밋 다음에 돌기 때문에 거부되지 않습니다. 두 파일에 이유를 주석으로 남겼습니다.

**셋. 우측 상단 닫기가 마우스로 눌리지 않았습니다.**
`.lobby-modal-commands`가 `inset: 0`이라 모달 전체를 덮는데, 자리만 잡는
층인데도 나중에 온 이 층이 닫기 버튼 위에 얹혀 **클릭을 가로챘습니다.**

**검사는 통과하고 있었습니다.** `.click()`은 히트 테스트를 건너뛰고 요소에
바로 이벤트를 보냅니다. 브라우저에서 `elementFromPoint`로 재서야 나왔습니다.
`pointer-events`로 고쳤습니다.

이 건의 회귀 검사는 **만들지 않았습니다.** jsdom은 스타일시트를 적용하지도,
화면을 합성하지도 않아 `pointer-events`를 확인할 수 없습니다. DOM 순서만
보는 검사를 쓰려다 **그건 통과만 하고 아무것도 구분하지 않는다**는 걸 깨닫고
지웠습니다. QA 12.7에 사람이 볼 항목으로 남겼습니다.

### 잰 것

375·1366·1920 세 해상도에서 모달이 CRT를 벗어나지 않고 비율 2.03을 지킵니다.
최소 글자는 11px입니다.

**본문 하한을 12px로 잡았습니다.** `.guide-lead`·`.guide-list`·`.lobby-controls`가
`0.93em`이라 본문이 11px이면 10.23px이 되어 `DESIGN_TOKENS` 8절을 어깁니다.
12 × 0.93 = 11.16px입니다. **리뷰 M-1과 같은 계열의 실수**를 하마터면 새로
만들 뻔했습니다.

가이드 5쪽 중 3쪽(`막는 경보`)만 본문이 6px 넘쳐 내부 스크롤이 생깁니다.
인계서가 허용한 범위입니다.

죽은 규칙도 함께 지웠습니다. `.lobby-guide`와 `.lobby-guide-pager` 계열이
렌더링 없이 남을 뻔했는데, 리뷰 C-1에서 지적받은 그 패턴입니다.

## 모달을 CRT 밖으로 빼고 키움 (2026-08-20)

**직접 보고 나온 요청입니다.** "모달창은 좀 크게 하자. 이건 모니터 화면 안에
들어와야 하는 건 아닌 것 같아."

맞는 지적이었습니다. 유리 안에 두니 본문이 **118px**밖에 안 나와 가이드
다섯 쪽 중 한 쪽이 계속 잘렸습니다. 인계서(`prompts/04`)가 "CRT 안쪽을
벗어나지 않아야 한다"고 지시했고 그대로 만들었는데, **그 제한이 어디서
왔는지를 따져보지 않았습니다.**

그림 속 모니터는 로비 화면의 무대입니다. 대화상자의 경계가 아닙니다.
씬 전체로 옮겼습니다.

| | 유리 안 | 씬 기준 |
|---|---|---|
| 모달 폭 (1366) | 366px | **900px** |
| 본문 | 320×118 | **787×258** |
| 본문 글자 | 12px | **14.7px** |
| 잘리는 쪽 | 1쪽 | **0쪽** |

**글자를 모달 폭에 묶었습니다.** `clamp(12px, 1.7cqw, 16px)`입니다. 그림이
커지면 글자도 같이 커져야 프레임과 내용의 비례가 유지됩니다. `.crt-display`가
`cqw`를 쓰는 것과 같은 이유고, 안 그러면 900px 창에 12px 글자가 떠서
프레임만 커진 꼴이 됩니다.

375에서는 여전히 20px 넘쳐 내부 스크롤이 생깁니다. 씬 자체가 349px이라
비율 2.03을 지키면 높이가 170px로 정해집니다.

**뒤집힌 지시를 원본에도 표시했습니다.** `prompts/04` 머리에 그 한 줄이
왜 바뀌었는지 적었습니다. 오늘 문서 여섯 군데가 실제와 어긋나 있던 것을
고쳤는데, 같은 일을 새로 만들지 않으려고요.

## 상사의 전화 규칙을 명세로 (2026-08-20)

"늦게 받으면 하트 하나 소실"이 정해지면서 `GAME_SPEC` 14절을 열었습니다.
13.10에서 "이번 범위 밖"으로 미뤄뒀던 것을 꺼냈습니다.

### 처음 쓴 안을 다시 짰습니다

처음에는 규칙을 그대로 받아 적었습니다. 다시 보니 **선택이 사라지는
설계**였습니다. 안 받는 값이 라이프 1개(전체 버퍼의 33%)면 최적 플레이가
"무조건 즉시 받기" 하나로 굳고, 그러면 `↓ 나중에`는 아는 사람은 절대 안 누르는
**초보만 벌하는 선택지**가 됩니다. 비용에 지배 전략이 있으면 선택이 아니라
세금입니다.

그렇다고 벌을 빼면 방해가 무시됩니다. 30초 게임에서 미묘한 벌은 안 보입니다.

**그래서 세금을 없애는 대신 딜레마를 한 층 위로 옮겼습니다.**
받는 것은 강제로 두고(늦으면 -1), 진짜 선택은 **상사의 지시를 따를지**로
만들었습니다. 따라서 틀리면 기존 오답 경로로 라이프를 잃습니다.
**라이프를 잃는 방법은 여전히 판정 하나뿐입니다.**

전화가 이 게임에서 유일하게 할 수 있는 일이 그것입니다. 카드도 메모도 전부
협조적이라 **플레이어를 더 맞게만** 만듭니다. 전화는 틀리게 만들 수 있는
유일한 요소이고, 그게 관제 업무의 진짜 난이도입니다.

### 짜다가 걸린 것

**상사가 항상 "통과시켜"라고 하면 안 됩니다.** 티어 3이 BLOCK 4 / ALLOW 1이라
지시의 **80%가 거짓**이 되고, "상사 말은 무시"가 새 정답표가 됩니다.

지시를 "통과시켜"와 "막아" 둘로 늘렸습니다. 거짓 지시가 오탐·미탐 어느
쪽으로도 갑니다. BLOCK 버튼을 앰버로 둔 2축과 같은 축입니다.

**큐를 건드리지 않고 참·거짓을 1:1로 맞추는 법**도 풀었습니다.
`remainingByTier[3]`의 맨 앞을 **뽑지 않고 들여다보면** 다음에 나올 티어 3
경보를 알 수 있습니다. 그것을 읽고 시드 난수로 지시를 고르면 봉지 순서와
무관하게 비율이 유지됩니다. 13.4의 "큐를 따로 손대지 않는다"가 지켜집니다.

**지배 전략을 없애는 규칙 둘**을 못박았습니다. 참인 지시는 카드만으로
확신할 수 없는 것을 확인해주고, **거짓인 지시는 그 카드에 반드시 반증이
있어야 합니다.** 반증 없는 거짓은 대조할 것이 없어 찍기가 됩니다.
심각도 93%, 표시 개수 93%와 같은 계열입니다.

버린 안 다섯 개도 이유와 함께 14.10에 남겼습니다.

### 덤으로 나온 것 — 티어에도 누수가 있었습니다

전화 설계에 쓸 재료를 찾다가 티어별 정답 분포를 처음 재봤습니다.

| 티어 | ALLOW | BLOCK | 한쪽으로 찍으면 |
|---|---:|---:|---:|
| 1 | 3 | 2 | 60% |
| 2 | 3 | 2 | 60% |
| **3** | **1** | **4** | **80%** |

전체는 ALLOW 7 / BLOCK 8로 거의 반반인데 **누수가 티어 3에만 몰려 있습니다.**

심각도는 감춰서 막을 수 있었지만 **티어는 난이도 구간을 알리는 장치라
감출 수 없습니다.** 게다가 크리티컬 경고음이 `tier === 3`에 걸려 있어서 그
소리가 "이제부터 막아" 신호로 쓰일 수 있습니다.

경고음을 심각도에서 티어로 옮길 때 "tier는 카드에 이미 표시되므로 소리로
새로 노출되는 정보가 없다"고 적어뒀는데, 맞는 말이지만 **티어 자체가 정답과
상관이 있다는 것을 그때 재보지 않았습니다.** 같은 검사를 한 축에만 돌린 것이
원인입니다.

`ALERT_DATASET.md`에 절을 신설하고 고칠 방향까지 적었습니다. 데이터셋을
바꾸는 일이라 **난이도 실험 20판이 끝난 뒤**입니다.

## 방향키로 화면을 고르게 함 (2026-08-20)

로비에서 시작해 일시정지·결과·모달까지 넓혔습니다. 옛 콘솔 메뉴는 방향키로
고르는 것이 자연스럽고, 근무 중 판정에 쓰는 손 모양과도 이어집니다.

**근무 중에는 절대 켜지지 않습니다.** 그때 좌우는 ALLOW·BLOCK 판정 키입니다.
켜는 조건을 훅이 아니라 **쓰는 쪽이** 정하게 했습니다. 훅이 스스로 판단하면
새 화면을 붙일 때마다 그 판단을 다시 맞춰야 합니다.

세 곳이 되면서 `useMenuKeys`로 뺐습니다. 모달은 창이 아니라 자기 안에서
키를 받으므로 훅을 그대로 못 쓰고, 방향 판별과 포커스 이동만 함수로
나눠 씁니다.

가이드에서는 좌우가 **쪽 넘김**입니다. 여섯 쪽을 읽는 동안 PREV·NEXT를 매번
찾아 누르게 하고 싶지 않았습니다. 쪽 넘김이 없는 설정에서는 좌우도 그냥
자리 이동이라 로비와 같습니다.

붙이면서 포커스가 사라지는 자리를 하나 찾았습니다. **첫 쪽에서 PREV를 누르면
그 버튼이 자기 자신을 비활성으로 만듭니다.** 그 순간 포커스가 body로 떨어져
방향키도 Tab도 시작점을 잃습니다. RESET도 되돌린 뒤 똑같습니다. 이제 닫기
버튼이 받습니다.

검사에서 키를 늘 모달에 쏘고 있었는데, **줄에 붙은 조작을 그냥 지나칩니다.**
포커스 가진 요소로 바꿨습니다. 안 고쳤으면 좌우 조작 검사가 전부 헛돌았을
겁니다. "목이 실물보다 관대하면 검증이 아니다"와 같은 계열입니다.

## 소리 크기를 3단계에서 5단계로 (2026-08-20)

`// MID` 한 마디뿐이라 지금 어디쯤인지, 얼마나 남았는지 안 보였습니다.
눈금과 백분율을 함께 두고 단계를 다섯으로 늘렸습니다.

**저장된 값이 문제였습니다.** 눈금이 늘면 같은 숫자 1이 다른 크기를 뜻하는데,
저장된 값만 봐서는 어느 시절 것인지 알 수 없습니다. 이름을 `volume`에서
`volumeStep`으로 바꿔 **없다는 것 자체를 옛 값이라는 표시로** 썼습니다.
옛 0·1·2는 새 0·2·4로 옮깁니다. 가장 작은 것과 가장 큰 것이 그대로 남는
자리입니다.

`v`는 올리지 않았습니다. **올리면 이전 키를 통째로 버려 최고 점수까지
사라집니다.** 필드를 더하는 것과 뜻이 바뀌는 것은 다른 문제고, 뜻이 바뀔 때
쓰는 수단이 이름입니다. `STORAGE_AND_RECOVERY.md` 2절에 규칙으로 적었습니다.

백분율은 처음엔 음량표에서 계산했는데, 5단계로 가면서 **방향을 뒤집었습니다.**
눈금을 고르게 나눈 뒤 그 비율대로 음량을 만듭니다. 이러면 화면의 60%가 진짜
60%입니다. 기본값은 가운데 60%이고 음량이 0.084라 3단계 시절 MID의 0.08과
거의 같아, 쓰던 사람에게는 소리가 그대로입니다.

## 캐릭터 초상 연결 — 같은 누출을 세 번째로 막았습니다 (2026-08-20)

코덱스가 만든 초상 8종을 픽셀 단위로 검수했습니다. PNG를 직접 디코딩해
전 픽셀을 세고, 브라우저 canvas로 한 번 더 확인했습니다. 128×128, 알파는
0과 255만, 지정한 여섯 색만 — 여덟 장 다 통과했습니다.

**문제는 그림이 아니라 어디에 붙이느냐였습니다.** 인계서가 고른 경보 둘
(`priv-esc`, `contractor-proddb`)은 **둘 다 정답이 BLOCK**입니다. 그대로
넣었으면 "얼굴이 있으면 차단"이 2/2로 맞는 규칙이 됩니다.

인계서는 "초상만 보고 정답을 추측하게 만드는 빨강/녹색 표시는 추가하지
않는다"고 적어뒀습니다. 맞는 경계인데 **초상이 있다는 것 자체가 표시라는
것을 놓쳤습니다.** 심각도 93%, 표시 개수 93%, 티어 80%와 같은 계열입니다.

ALLOW 정답 둘(`backup-job`, `traffic-spike`)에도 붙여 2:2로 맞췄습니다.
넷 다 사람이 벌인 일이라 당사자 얼굴이 어색하지 않은 경보입니다. 얼굴 없는
나머지 11장도 ALLOW 5 / BLOCK 6이라 반대편도 쏠리지 않습니다.

`portraits.test.ts`가 양쪽을 다 검사합니다. **인계서대로 BLOCK 둘만 넣으면
이 검사가 실패하는 것까지 확인했습니다.**

세 번 같은 실수를 겪고 나서 규칙으로 적었습니다. **화면에 표시를 하나 더할
때마다 정답과의 상관을 잰다.** 티어 때는 재지 않아 놓쳤습니다.
